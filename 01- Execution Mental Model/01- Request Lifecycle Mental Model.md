## Client Server Architecture
أغلب الـ Web حاليا شغال بالمعمارية دي، أنت بيكون عندك الـ Browser عارض الداتا اللي جاية من الـ Server أو الـ Backend *بتاعك*، قاعدة أساسية هنا أن الـ Client هو دايما اللي بيبدأ الـ Hit هو دايما اللي بيدي طلب أو Request للسيرفر أنه يشتغل مش العكس، ولما السيرفر بيتبعتله Request لازم يكون في Response جاي من السيرفر في الرد سواء العملية نجحت أو فشلت

****
## Finding The Server (DNS)
الـ DNS هو اختصار لـ Domain Name System
أحنا أي موقع بيكون لي Domain زي `google.com`
بس الـ Domain ده مجرد شكل أنما كل موقع بيكون لي IP Address
هو العنوان الحقيقي للموقع زي كدا `142.251.36.46`

أحنا كمستخدمين مش مطلوب منا نحفظ الـ IP فبنكتب على طول الـ Domain

هنا لما تيجي تطلب موقع أو Domain بتحصل عملية
### DNS Resolver
الـ DNS بيدور في حاجة زي Dictionary بيترجم الـ Domain لـ IP بس هو بيجيبه منين؟
هنا بيعتمد على طبقات
المواقع اللي أنت بتبحث عنها كتير المتصفح بيحفظها في Cache على جهازك عشان يشغلها في جزء من الثانية من غير ما يخرج برا

لو دخلت بقى على موقع مش متكيش على الجهاز، المتصفح بيبعت للـ **DNS Resolver** سواء بتاع مزود النت أو Google أو Cloudflare، الـ Resolver ده هو اللي بيلف ويسأل سيرفرات الـ DNS بالترتيب لحد ما يوصل للسيرفر الأصلي للموقع ويجيب منه الـ IP النهائي، فبعد الرحلة دي البراوزر بياخد الـ IP اللي هيدخل عليه عشان يوصل للي هو عايزه
****
## فكرة الماسورة
ببساطة أنت أول ما الموقع يترجم الـ Domain ويوصل بالـ IP بتحصل حاجات بقى في طبقة الـ Transport Layer

ببساطة أنك بتفتح زي ماسورة بين البراوزر او الكلاينت بتاعك والسيرفر، عشان تبعت من خلالها الـ APIs أو الـ HTTP Requests بتاعتك كلها

فطبعا الماسورة بتضبطها بحاجتين اولا انك تعمل الماسورة وأنك تخلق نظام حماية بينك وبين السيرفر عشان لما تنقل حاجة للماسورة
محدش يعرف يدخل ويسرقها منك عشان لو دخل ببساطة هيلاقي الداتا متشفرة بقفل وحماية ميعرفهاش غير البراوزر بتاعك والسيرفر بس

## TCP Connection

![](https://res.cloudinary.com/du7j80lol/image/upload/v1790521205/obsidian/nppb59bfhfuzpvukqfz3.png)

بعد ما البراوزر بيعرف هو رايح فين ويوصل للـ IP بتيجي الخطوة الجديدة وهو انه يفتح TCP Connection مع السيرفر اللي عايز يروحلها

أول خطوة الكلاينت بيبعت SYN عشان يفتح مع السيرفر كونيكشن
بتيجي بعدها خطوة الـ SYN-ACK السيرفر بيلقط الطلب وبيقول أنه جاهز
بعدها الـ Client بيرد بـ ACK وهنا الكونيكشن اتفتح خلاص

ومن هنا البراوزر بيبدأ يبعت الـ HTTP Request

لو الموقع شغال HTTP البراوزر كان هيبعت الداتا زي ما هي وده طبعا شيء غلط، فمن هنا أحنا أكيد بنتعامل مع HTTPS فهنا في خطوات زيادة بعد الـ Connection مع السيرفر.
### TLS Handshake (Transport Layer Security)
TLS handshakes occur after a TCP connection has been opened via a TCP handshake.

هنا عشان الموقع HTTPS بنزود الخطوة دي بعد الـ TCP وهي أنه بيعمل حاجة اسمها `CLIENTHELLO` في الخطوة دي الكلاينت بيقول للسيرفر شوية حاجات
1. ايه الـ TLS Version اللي انت بتدعمه
2. ايه الـ Cipher Suite اللي بتدعمها ودي عبارة عن مجموعة من الـ Encryption Algorithms عشان تـ Encrypt الـ Data

بعدها السيرفر بيرد بـ `SERVERHELLO` بعد ما يختار الـ Version والـ Suite المناسبة
وبيبعت **Certificate** للـ Client ودي بتكون جواها الـ Public Key اللي من خلاله الـ Client بيشفر الداتا ودي حاجة اسمها **Asymmetric Encryption** وهي أن الكلاينت بيشفر الداتا بالـ Public Key حطلها قفل بس هو معهوش مفتاح
الوحيد اللي معاه المفتاح هو السيرفر وده الـ Private Key ومش موجود غير في السيرفر

المشكلة أن العملية دي عملية صعبة جدا ومعقدة جدا وبتاخد وقت، فلو كل مرة الكلاينت بعت حاجة عمل كدا فكدا كارثة، فمن هنا في حاجة تانية بتحصل

لما الـ Client بيمسك الـ Public Key أول مرة بيعمل زي Secret بيكون Symmetric Key عادي ويبدأ يقفله بالـ Public Key ده ويوديه للسيرفر

السيرفر بيفك الـ Key بالـ Private Key ويعرف الـ Symmetric Key وبكدا بقى معاهم شفرة بينهم وبين بعضيهم عارفين يتكلموا بيها وبتكون سهلة بتكون Symmetric بتاخد اقل من مللي ثانية حرفيا وسريعة جدا للفك بس محدش يعرفها غير الكلاينت ده والسيرفر

من هنا أنت جهزت الماسورة خلاص عملت TCP Connection و ضبطت الـ TLS
فدلوقتي بقى تبدأ تبعت HTTP Requests و Responses بينك وبين السيرفر براحتك وعيش وتستخدم حاجات ال Application Layer زي الـ API والـ Token والحاجات العادية دي وبراحتك

## What And Why HTTP?
هي اختصار لـ **Hypertext Transfer Protocol** أحنا كـ Software Engineers بنستعمله عشان يكون **Contract** أو لغة تخاطب بين الـ Client والـ Server بتاعنا، وده عشان عوامل كتير من أهمها:
- الـ **Stateless**: أي طلب بتعمله بيه بيكون مبعوت فيه كل الخصائص بتاعته، طلب الـ HTTP بتبعت الريكوست وتودي الريسبونس مرة واحدة وتختفي بعدها الطلب ده مبيبقاش لي وجود، فعشان كدا بنحط كل حاجة تخص الـ Request جواه مرة واحدة
- انه **Human Readable**: أنت تقدر تقرأ الريكوست والريسبونس بشكل واضح لأنه مكتوب *Text Based*

الـ HTTP Request اللي ماشي في الماسورة أيا كان بيكون حامل حاجات معينة وبتتكرر كل مرة بالمناسبة لأنه Stateless
- **الـ Method / Status Code:** الفعل المطلوب (`GET`, `POST`...) أو النتيجة اللي راجعة (`200 OK`, `404 Not Found`...).
- **الـ Headers:** الميتاداتا (زي `Content-Type: application/json` أو التوكن).
- **الـ Body:** الداتا الفعلية المشحونة (الـ JSON).

## Where Does The Request Go? (Kestrel Web Server)
أول ما الريكوست يوصل للسيرفر بيوصل عبارة عن Bytes على كارت الشبكة، نظام التشغيل مش بيفهم يعني ايه C# ولا دوت نت

فهنا بيجي دور **Kestrel**
هو الـ Web Server الإفتراضي لـ ASP.NET Core مصمم يكون سريع جدا وخفيف و Cross-Platform

ولي كذا دور:
1. الـ **Listnen**: بيسمع البورت اللي شغال وبيستنى أي حاجة منه
2. الـ **Parsing**: بيمسك الـ Raw Bytes اللي جاية من *الماسورة* ويقرأها كـ HTTP Format
3. الـ **Object Creation**: بيحول النص الـ HTTP لاوبجيكت يفهمه C# اسمه `HttpContext`

بعد ما Kestrel ينشئ الـ `HttpContext`، بيسلمه لأول محطة في دوت نت وهي الـ **Middleware Pipeline** عشان يمر بالفلترة والـ Routing ويوصل للكود بتاعك.
